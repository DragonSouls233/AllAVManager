## 五、能不能直接用到 MDCX —— 分级

### T1 · 有明确落点，建议排期

**1. `ref155-crawlerx` —— 22 个新站点适配器（最高价值）**
实际覆盖站点：Aisex、Avfan、Avjoho、CaribbeanCom、Duga、Eporner、Fc2、FfJav、Heyzo、Jable、JavBus、
JavDatabase、JavDb、JavLibrary、JavPhotos、Javbtc、MinnanoAv、Missav、OneFourOneJav、OnePondo、Onejav、
TokyoHot、Warashi、Xcity。
→ MDCX 现在只覆盖 javdb / javmenu / javmost / javbus / dmm / thejavdb / avmoo / javplace / javdatabase 等，
**Aisex、Avfan、Avjoho、CaribbeanCom、Duga、Eporner、FfJav、Heyzo、JavPhotos、Javbtc、MinnanoAv、
OneFourOneJav、OnePondo、Warashi、Xcity、TokyoHot 这 16 个是纯新增**。
→ 同时它的 `Contract` 目录是一套**能力接口**（`DetailCapable` / `GalleryCapable` / `ListingCapable` /
`PerformerListingCapable` / `PerformerSearchCapable` / `LoginCookieProvider`），配合
`AdapterManifestRegistry` 做「清单声明 vs 实现」校验。这套抽象比 MDCX 的 `supported_types` 更细。
→ 许可证 **MIT**。

**2. `ref152-embymetaeditor` —— 三个可独立搬的机制**
- **离线资料库优先**：把 `data/actresses_export.csv`（2.7 万条）`//go:embed` 进二进制，排在所有在线源**最前面**
- **别名记忆落盘策略**：只在「人工采用 / 写入成功」时才落盘，之后所有源共享；**只加搜索词，不放宽身份阈值**
- **写入前 dry-run + 快照回滚**：批量写入前逐字段新旧对照，写完可逐字段回滚
→ 对应 MDCX：`actor_name_guard` / `actor_name_condition` / 缺口体检的批量写入，都缺「写入前后对照 + 回滚」。

**3. 番号清洗规则（两个独立来源互相印证）**
- `ref195-jav-scraper`（MIT）：剔除发布站网址 / 域名 / 水印前缀（如 `hhd800.com@`）
- `ref177-javcover_insert`：剥离 `[SHT] …_FHD` 之类干扰、`h_086ssni123` 深度正则
- 两者都做**中文字幕标识别**：数字后紧跟 `C`/`c`（如 `CESD194C` → `CESD-194`），并在 NFO 写中文字幕标签
→ 直接补进 `app/scraper/number.py` + `extract_fc2_id()` 同级的位置。

**4. `ref177-javcover_insert` —— 媒体结构修复**
MP4 `dat` atom 损坏修复（LosslessCut 等造成）、**moov 前置 faststart**、封面裁剪 378:538 用 Mutagen 注入、
跨盘（exFAT/NTFS）`rename` 失败降级为「拷贝 + 抹除」。
→ MDCX 已有 ffmpeg 相关处理，但「原子级校验 + 修复」这条值得对照。

**5. 新下载源（Jable / MissAV / SupJav）**
`ref200-jable-downloader-cli`（三源并行解析 + 按分辨率/码率选最佳 HLS + 拒绝 6 秒广告/短预览/空清单）、
`ref179` / `ref161` / `ref180`（Rust 核心与 GUI）。
→ MDCX 的 `m3u8_engine` / `universal_downloader` 可增源；「多源并行探测 + 逐条验证时长」的策略值得抄。

**6. `ref181-gfriends-bot` / gfriends 头像数据 —— 只借索引与 CDN 容错细节**
十万级演员头像数据（`Filetree.json` 索引 + jsDelivr CDN 双层容错）。
→ **`gfriends/gfriends` 本体未收录**（用户已自备数据，且 MDCX 图片一律后台刮削，无需本地副本）；
只保留了 `ref181-gfriends-bot` 供参考其匹配/下载策略。MDCX **已有** `routes/gfriends.py` + `gfriends_importer`，本项价值仅在索引与容错细节。

**7. `ref160-javdb-scraper` —— 另一条 CF 绕过路线**

**8. `ref196-jd-online` —— CloudDrive2 的纯 Python gRPC h2c 实现**

## 六、与 MDCX 已有能力的重叠（避免重复造轮子）

本次核查 MDCX 源码，以下能力**已经存在**，不要因为「参考库有」就重做：

| 参考库做法 | MDCX 现状 |
|---|---|
| crawlerx 的「自适应抓取降级链」 | **已有** `app/utils/cf_bypass.py`：`CurlCffiStrategy` → `CfWorkerProxyStrategy` → `FlareSolverrStrategy` → `FallbackCacheStrategy`，含 `CloudflareBypass` 单例与 `cf_fetch()` |
| gfriends 头像接入 | **已有** `app/api/routes/gfriends.py` + `gfriends_importer._find_avatar_url`（支持 `name` 与 `name_jp` 双路匹配） |
| jable-downloader 的多源 HLS 选流 | **部分已有** `app/services/download/m3u8_engine.py` |
| MP4 faststart | **已有** `movies.py` / `workflow.py` 中已有 faststart 处理 |
| 演员名矫正 | **部分已有** `app/crawlers/wiki_amateur.py` |

**结论**：crawlerx 不可替代的部分是「**16 个纯新增站点的 HTML 解析规则**」和「**能力接口抽象**」；
其余多为「思路可抄、代码不必移植」。
（gfriends 头像数据**未收录**——用户已自备，且 MDCX 图片一律后台刮削，不需要本地副本。）

### 本轮踩过的坑（避免重踩）

1. **`.git/config` 里被写死的失效代理** `http://127.0.0.1:10664` 覆盖了全局可用的 `socks5:10808` → 已清除。
2. **代理比直连慢 15 倍**（0.14 MB/s vs 2.11 MB/s）→ 批量克隆一律直连。
3. **PortableGit 系统级 `credential.helper=helper-selector`** 会让缺失仓库的克隆**弹窗挂死**（曾观察到 290 个 helper 进程），
   批量脚本必须带 `GIT_CONFIG_NOSYSTEM=1` 且 `credential.helper=` 置空。
4. **`subprocess` 超时只杀父进程**，孙进程 `git-remote-https` 会占住管道造成假死 → 必须 `taskkill /F /T` 杀整棵树，
   且输出要重定向到文件而不是管道。
5. **同一个仓库目录被两个脚本实例同时操作**（`rm -rf` 互删 + 编号互撞）→ 落地脚本必须做「已存在即复用」的判据，
   而不是每次重新分配编号。
6. **`core.autocrlf=true`**：用同步工具写入的 md 是 CRLF，`HEAD` 里存的是 LF ⇒ 每次 `git add` 都整文件重写。
   追加内容时顺手统一为 LF，diff 才干净。
7. **仓库自带大体积二进制**（如 `JAV_MovieManager` 里 211MB 的 PotPlayer）→ 用
   `--filter=blob:none --no-checkout` + `sparse-checkout` 排除，落盘仅 8.9MB。
