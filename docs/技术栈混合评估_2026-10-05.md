# MDCX 技术栈混合评估

> 日期：2026-10-05
> 触发问题：「有没有需要混合技术栈？不要纯 Python，适当用其他语言是不是更好？特别是参考库里纯 Python 的应该不多。」
> 结论：**不需要为了换语言而换语言。** 参考库恰恰以 Python 为主（46/78），且 MDCX 运行时本来就已经是混合栈。真正该混的地方很窄，且有前置条件。

---

## 一、先纠正一个事实前提

对 `G:/MDCX/.references/MDCX-Project-Reference` 全部 78 个有效子模块按**主语言**（源码文件数最多的语言）做了统计：

| 主语言 | 项目数 | 占比 |
|---|---|---|
| Python | **46** | **59%** |
| TypeScript | 14 | 18% |
| JavaScript | 8 | 10% |
| Go | 7 | 9% |
| C# | 2 | 3% |
| PHP | 1 | 1% |

> 统计口径：每个项目在 maxdepth 3 内分别统计 `.py/.go/.cs/.ts/.tsx/.js/.php` 文件数，取最多者为主语言。

**Python 是绝对主力，占近六成。** 「参考库里纯 Python 不多」是一个错觉——产生错觉的原因是：少数非 Python 项目（amane、metatube、AVDC）功能太亮眼，记忆权重被放大了，而大量 Python 项目因为形态相似（都长得像 javbus/javdb 爬虫）被忽略了。

许可证分布（能识别到 LICENSE 的 51 个）：MIT 27、无 LICENSE 20、Apache 2、GPL 1、BSD 1。**无 LICENSE 的 20 个占近四成**，这些一律「保留一切权利」，只读不抄。

## 二、MDCX 现状：本来就是混合栈

「不要纯 Python」这个目标其实**已经达成**，只是不在源码文件层面体现：

| 层 | 技术 | 语言 |
|---|---|---|
| 前端 | Vue 3 + Electron + Vite | JS / TS |
| 业务编排 | FastAPI 路由 / 刮削引擎 / 字段合并 / 调度 | Python（522 文件、17.9 万行） |
| 原生扩展 | lxml、selectolax（lexbor）、NumPy、Pillow、curl_cffi | C / C++（以 Python 扩展形式加载） |
| 外部二进制 | ffmpeg / ffprobe / ffplay、xray、yt-dlp | C、Go、Python |
| 桌面壳 | pywebview、pystray、PyInstaller | Python + 原生 |

**关键点**：Python 真正不擅长的地方，早就已经被推给了 C 层——HTML 解析走 selectolax（C 的 lexbor），图像走 Pillow（C），数值走 NumPy（C），视频走 ffmpeg（C 子进程），反爬 TLS 指纹走 curl_cffi（BoringSSL 的 JA3 伪装，**这是整个项目最有价值的非 Python 组件**）。

剩下的 Python 代码几乎全是 **I/O 密集型**（HTTP 抓取、SQLite 读写、文件遍历），asyncio 处理这类负载本来就是强项。**把 I/O 密集的编排逻辑改写成 Go，不会更快，只会更难维护。**

## 三、判断准则

不要问「参考库用什么语言」，要问三个问题：

1. **这个工作负载是 CPU 密集还是 I/O 密集？** —— I/O 密集（抓取、DB、文件元数据）→ Python 够用；CPU 密集（批量哈希、图像变换、压缩、全文检索）→ 才考虑编译型。
2. **瓶颈真的被量出来了吗？** —— 没有 profiler 数字支撑的重构一律不做。参考库项目是独立 CLI / 单文件服务，目标和 MDCX（集成式应用 + Windows 部署 + 看门狗计划任务）完全不同，语言选择没可比性。
3. **换语言能带来多少收益，代价是多少？** —— MDCX 现在部署链路是：venv + SSH/SMB 拷文件 + 清 `__pycache__` + `schtasks` 重启 + 看门狗兜底。**再加一条编译工具链，等于把这条本已脆弱的链路复杂度翻倍。**

## 四、值得混的地方（窄、可测量）

按优先级排列，**全部以「实测出瓶颈」为前置条件**：

### P0 — 批量媒体计算 sidecar（Go 首选 / Rust 次之）

**场景**：全库级别的指纹计算、精灵图/VTT 生成、媒体探测、海报增强、人脸裁剪。当前实现是 Python 循环 + 每个文件起一次 ffmpeg 子进程。

**真正的低效点不在数学**（ffmpeg 已是 C），而在：
- 进程编排开销：Python 侧逐个 `create_subprocess` + 解析输出
- 并行度控制粗：没有按 CPU 核数调度的 worker 池
- 无增量清单：重跑整个库，不认已计算结果
- 进度持久化弱：中断即从头

**建议形态**：一个 `mdcx-core` CLI，输入目录清单，输出 JSONL 计数清单，Python 以子进程调用（**与 ffmpeg 完全同一模式**）。
**选 Go 的理由**：参考库 Go 项目最多（amane / metatube / atlas），可直接读实现思路；静态单文件，交叉编译到 Windows 零依赖；与 xray 一致。
**不选 Rust 的理由**：性能红利在此场景几乎吃不到（瓶颈在 ffmpeg），但学习与编译成本高得多。

### P0 — 自适应限速 / 人类化抖动（可留在 Python）

这一项**不需要换语言**。参考库里 `ref99-javorganizer` 的 `AdaptiveThrottle.cs`（MIT）、`ref58-javspider_stack`（Python，MIT）都是算法参考，用 Python 重写即可。属于「抄算法不抄语言」。

### P1 — 库范围全文/模糊检索（仅在库规模撑不住时）

若作品数到 10 万+ 且 `LIKE` 查询成瓶颈，可考虑 SQLite FTS5（仍是 SQLite，非换语言）→ 再不行才上 tantivy / meilisearch sidecar。目前数据规模未知，**先测量**。

### P1 — TLS 指纹进一步强化（仅在 curl_cffi 被封时）

若 curl_cffi 被目标站识别，可上 Go + utls 的抓取 sidecar。但 curl_cffi 目前工作良好，**属于防御性预案，不是待办**。

## 五、不该混的地方（明确劝退）

| 不要做的事 | 原因 |
|---|---|
| 用 Go/C# 重写抓取引擎 | 网络 I/O 主导，性能无收益；且会摧毁 canon 源序、熔断器、轮换编排等一整套已验证逻辑 |
| 用 Go/C# 重写 API 层 | FastAPI 的 Pydantic 校验 + 自动文档无可替代，且无性能压力 |
| 把合并逻辑（merger）搬出 Python | 依赖字段优先级、三值布尔、白名单等大量业务语义，跨语言只会引入不一致 |
| 因为「参考库是 Go」就跟进 | 参考库是独立工具，与集成式应用的约束条件完全不同 |
| 用 Cython / C 扩展改写业务代码 | 编译型扩展部署到 Windows 服务器需现场编译器，收益与成本严重不成比例 |
| 把 SQLite 换成 PostgreSQL/MySQL 服务 | 单机嵌入式场景，SQLite 更简单更稳；换服务只增加运维面 |

## 六、推荐架构结论

**「Python 当编排器 + 编译型 sidecar 只做批处理」**，且满足：

1. 先有 profiler 数据，再决定是否引入；
2. 走**进程边界**（subprocess + JSONL / stdio），**不用 ctypes/FFI**——FFI 是 bug 高发区，且崩溃会拖垮整个 Python 进程；
3. sidecar 必须是**静态单文件、零运行时依赖、可交叉编译到 Windows**（这是选 Go 而非 Rust / C# 的决定性理由）；
4. sidecar 只做**无状态纯计算**，不碰数据库、不碰业务规则、不碰网络编排；
5. 保留 Python 侧的降级路径：sidecar 缺失时回退到现有的 ffmpeg/NumPy 实现，保证不因一台机器没装 `.exe` 就整体瘫痪。

**一句话**：MDCX 已经是混合栈了，而且混合得很合理。下一步不是「扩大混合面」，而是「在实测出真正的 CPU 瓶颈时，加一个进程级 sidecar」。在此之前，任何语言迁移都是负收益。
