## SQLAlchemy 连接池泄漏根治（GC 警告 "non-checked-in connection"）

### 根因
大量路由/服务用 `session = await mod_db.get_session()` 或 `await get_module_session(module)` 获取**裸** `AsyncSession`，但调用方从不 `await session.close()`（如 movies.py 几十个 endpoint、jav_routes/fc2_routes 等）。连接长期不归还池，最终靠 GC 回收并触发 SAWarning，高并发下可能耗尽 pool_size=10+overflow=20。

主库 `app.db.database.Database` 通过 `async with db.session()` / `async with get_session()` 自管理，不泄漏；仅 `ModuleDatabase`、`SystemDatabase` 的 `get_session()` 返回裸 session 泄漏。

### 修复（根治而非抑制警告）
1. **新增 `app/db/session_registry.py`**：ContextVar 登记表 + `register_session()` + `close_registered_sessions()` + `session_cleanup_middleware(request, call_next)`。中间件在响应送出后(finally)统一 `await session.close()` 归还连接池。
2. **`module_db.py`**：`get_session()` 创建 session 后调 `register_session()`；新增 `session_scope()` async context manager（异常自动 rollback，替代裸 get_session）。
3. **`system_db.py`**：`get_session()` 同样登记。
4. **`main.py`**：最内层注册 `app.middleware("http")(session_cleanup_middleware)`。
5. **`stats.py` dashboard**：`mod_session = await get_session()` + try/finally 改为 `async with mod_db.session_scope() as mod_session:`。

### 历史修复确认已在 G 盘源码（之前已修，本次复核）
- `_module_mixins.py`:30 `title_jp: Mapped[str|None]`（修 /api/v1/movies 500 AttributeError）
- `gfriends_importer.py`:354 `WHERE 1=1` 保底（修 SQL near "AND" 语法错）
- `bin_tools.py`:13 `APP_ROOT = ...parent.parent.parent`（修 ffmpeg/yt-dlp 路径少算一层）

### 部署
覆盖 E:\MDCX-Server 对应文件（新增 session_registry.py 必须带过去）+ 重启。若服务器库仍缺 title_jp 列则删库重建。

### 技术要点
- `_request_sessions` 用 ContextVar 保证请求隔离；每个请求 middleware 用 `set([])` + `reset(token)` 防并发串。
- 已 `async with` 管理的 session 重复 close 幂等，无副作用。

## 扫描计数 vs 库/首页/补刮数值不一致 根因排查（2026-08-05 15:xx）

### 用户现象
扫描日志报"新增 N 部"，但首页(dashboard COUNT(*))、影片库(list_movies)、补丁刮削(detect_missing) 显示的是另一（老）数值，新增加的没反映进去。用户怀疑扫描计数是"假的"。

### 排查结论
1. **架构确认**：无中心数据库（scraper.db 已清理，开发机 data/database 现为空的）。所有读写均为逐模块库 jav.db/fc2.db/...，`ModuleDatabase.get_instance(name)` 单例，扫描与查询同一物理库。
2. **扫描器写入正确**：`jav_scanner._scan_directory` 写 `JavMovie`，新片 `status="pending"`，`movies_added` 在 `commit()` 前 `+1`（乐观计数）。核对 `MovieMixin`：扫描器未赋值的列（title_jp/plot/release_date...）全为 Optional 或有默认 → 单纯漏赋值不会致 commit 失败。
3. **真因（扫描假计数的根因）**：`ModuleDatabase.init()` 用 `metadata.create_all`，**只建缺失表、不给旧表加新列**。服务器 jav.db 是在 title_jp/plot_short/studio_id 等列加入模型前创建的（之前 title_jp 的 500 即证据：模型已更新、旧表无列）。扫描 INSERT 带 title_jp → SQLite `no such column` → **整批 commit 回滚**，而 movies_added 已 +1 → 扫描报新增、库里 0 条 → 首页/库/补刮全显示老数值。
4. **补刮第二处 bug**：`patch.detect_missing` 未传 module 时 `MissingDetector(module_name=None)` 读中心库 scraper.db（已废弃）→ 看不到 jav.db 新片 → 补刮计数不涨。

### 修复
- `app/db/module_db.py`：`init()` 在 `create_all` 后调用新增的 `_migrate_schema(conn)`。遍历模型元数据，对旧表缺失列执行幂等 `ALTER TABLE ADD COLUMN`（用 `str(col.type)` 作为 SQLite 类型；NOT NULL 无默认时降级为 DEFAULT NULL 防失败）。→ **旧表自修复，扫描 INSERT 不再回滚，计数变真**。无需删库重建。
- `app/api/routes/patch.py`：`detect_missing` 未传 module 时改为遍历 jav/fc2/uncensored/chinese/western/pornhub 各模块库聚合检测（`_detect_across_modules` 辅助函数）；传 module 时仍读该模块。文档字符串同步更新（不再依赖中心库）。

### 验证要点
- 部署后重启，启动日志应出现 `补齐缺失列 title_jp (VARCHAR(500))` 等；之后扫描新增会真实落库。
- 注意：`run_patch`（执行补刮）走 `PatchOptions(module=request.module)`，前端执行时通常带 module；module=None 仍读中心库属另一路径，本次未改（不在计数不一致范围内）。

### 用户痛点
服务器启动崩溃（如 NameError / 迁移失败 / SystemExit）后，Windows 托盘/双击启动的黑窗口一闪而过，控制台 stderr 随窗口关闭丢失，且 `data/logs/app.log` 每次启动被清空，早期崩溃抓不到 → 完全无法定位原因。

1. `setup_logging()` 原在 `lifespan` 内部才调用 → 更早的导入期/启动期崩溃不落盘。
2. `LOGGING_CONFIG` 的 handler 全是 `StreamHandler`，**零文件 handler**；且 `"app"` logger 设 `propagate: False` → 应用日志永不写文件，app.log 长期是空文件。

### 修复（新建 1 + 改 5）
- **新增 `app/utils/crash_logger.py`**：零依赖（仅标准库）"最后一道防线"。
  - `resolve_log_dir()`：`MDCX_DATA_DIR` 环境变量 > 项目根 `data/` > cwd `data/` > tempfile 兜底（保证任何阶段都能拿到可写目录）。
  - `log_crash(exc_type, exc_value, exc_tb, context)`：追加写 `crash.log` + `_env_snapshot()`（Python 版本/平台/PID/命令行/工作目录/数据目录）+ 完整 traceback。
  - `install_crash_handlers()`：`sys.excepthook` / `threading.excepthook` / asyncio 异常处理器，幂等。

  - `bootstrap_logging()`：早期 `RotatingFileHandler` 写 `startup.log`，标记 `_mdcx_bootstrap=True`（供后续 setup_logging 保留、不清掉）。

## 19:14 修复 GET /api/v1/subscriptions 500 (no such table: actor_subscriptions)

### 用户现象
服务器日志：`GET /api/v1/subscriptions → 500`，`sqlalchemy.exc.OperationalError: no such table: actor_subscriptions`。其余接口（头像/封面/扫描）均 200，唯独订阅接口崩。

### 根因（两层）
1. **路由用错数据库会话（直接触发 500 的根因）**
   - `app/api/routes/subscriptions.py` 注入 `from app.db.database import get_session` → 这是**系统库 system.db** 的会话。
   - 但 `ActorSubscription` 模型定义在 `app/db/jav_models.py`：`class ActorSubscription(ActorSubscriptionMixin, JAV_BASE)`，`__tablename__="actor_subscriptions"` → 表挂在**模块库 jav.db**（JAV_BASE 元数据）里。
   - 路由用 system.db 会话去 `SELECT ... FROM actor_subscriptions` → system.db 无此表 → `no such table`。
   - 验证：用服务器 Python3.14 导入 `JAV_BASE` 确认 `actor_subscriptions` 在其 metadata 内，`create_all` 能产出该表；列含 id/user_id/actor_id/notify_new_movie/last_checked_at/last_movie_count/created_at 等，正是 service 读取的字段。说明表会随 `ModuleDatabase.init_all()` 在重启时建好，之前只是查错了库。

2. **actor_subscription.py service 内有 3 个函数引用未定义变量（潜伏性 NameError）**
   - `check_new_movies_for_actor` / `check_all_subscriptions` / `list_new_movies_for_subscription` 直接用了 `ActorSubscription`/`MovieActor`/`Movie`（及 `Actor`），但函数体内从未 `get_module_model(...)` 定义它们（只有 list_subscriptions/subscribe/unsubscribe/is_subscribed 定义了）。
   - 这三个端点一旦被调用就会 `NameError`，是下一个必然出现的 500。

### 顺带修复的同族 bug
- `app/api/routes/series_subscriptions.py`：同样注入 `get_session()`（system.db），且把该 session 当成 `module` 实参传给了 service（service 内部自开模块会话、签名无 session 参数）→ 调用必崩。改为移除 session 依赖、显式传 `module`。
- `app/services/subscription_downloader.py`：`check_all_subscriptions(module=module)` 实参数目不对（actor service 该签名是 `(session, module="jav")`）→ 改为 `check_all_subscriptions(session, module=module)`。
- `app/services/telegram_bot.py`：`/subscribe`、`/list_subscriptions` 命令调用 `subscribe(...)`/`list_subscriptions(...)` 时漏传必填的 `session`（module 字符串被绑到 session 形参）→ 崩溃。补 `session=session`。

### 改动文件（均需覆盖到 E:\MDCX-Server 后重启）
- `app/api/routes/subscriptions.py`：新增 `_subs_session` 依赖用 `get_module_session(module)`，所有端点改用模块会话并透传 `module`（默认 jav，向后兼容前端不传 module）。
- `app/api/routes/series_subscriptions.py`：移除 system.db 会话依赖，改为显式传 `module` 给 service（service 自开模块会话）。
- `app/services/actor_subscription.py`：给 `check_new_movies_for_actor`/`check_all_subscriptions`/`list_new_movies_for_subscription` 增加 `module` 形参并在函数体顶部 `get_module_model` 定义 Actor/ActorSubscription/MovieActor/Movie。
- `app/services/subscription_downloader.py`：修正对 actor service `check_all_subscriptions` 的调用签名。
- `app/services/telegram_bot.py`：给 `subscribe`/`list_subscriptions` 调用补 `session=session`。

- 服务器 Python3.14 实测：`actor_subscriptions` 注册于 `JAV_BASE.metadata`=True；`create_all` 产出该表=True；列齐全。

## 21:05 第三批：修复 自动整理定时任务 `no such table: auto_organize_rules`

日志：`app.main - ERROR - 自动整理定时任务异常: (sqlite3.OperationalError) no such table: auto_organize_rules`。

根因（同款「错库会话」）：
